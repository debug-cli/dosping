What is DOSping

DOSping ( /duːz/ /pɪŋ/ ) is a terminal-based network stress testing tool. It opens hundreds of concurrent TCP connections to a target IP address while simultaneously monitoring whether the target is still responding. The interface shows three live panels side by side: the flood log, the connectivity monitor, and a real-time stats sidebar.

Built with Python, Textual, Rich, and asyncio. Runs on Windows, Linux, and macOS.

What makes it different

  • Live split-panel UI showing attack output and connectivity status simultaneously
  • Real-time stats: connections per second, success rate, bytes transferred, latency
  • Multi-tab sessions: run up to 4 tests against different targets at the same time
  • Three view modes (Skid, Advanced, IT) controlling panel visibility and detail level
  • Command palette with 11 actions for controlling tests without memorizing shortcuts
  • Log export for post-test analysis
  • Session summary printed to terminal on exit

Splash Screen

The first thing you see on launch. A matrix-style character reveal sweeps left to right across the DOSping ASCII logo. Random characters from the glitch set (!@#$%^&*01█▓▒░╬╠╣╦╩╗) appear and resolve into the correct characters as the sweep passes.

Below the logo, a KITT scanner bar (bouncing glow, left and right) runs continuously. The animation runs at 25 fps. Press any key to advance.

How the animation works

  1. A reveal_col counter increments each frame (40ms)
  2. Characters to the left of reveal_col render in their final form
  3. Characters within 3 columns of the sweep render as random glitch characters (40% chance of real character, 60% random)
  4. Characters to the right render as dim random characters (18% visibility)
  5. Once reveal_col passes the end, the full Rich-markup logo replaces the animation

Scanner Engine

The scanner is implemented in scanner.py as a pure-Python async engine. No nmap, no external tools, no administrator privileges required.

How it works

  1. Creates an asyncio.Semaphore(concurrency) to limit parallel connections
  2. Spawns one asyncio.Task per port via asyncio.gather()
  3. Each task attempts asyncio.open_connection(host, port) with a configurable timeout
  4. On success, sends a port-specific probe (HTTP GET, SMTP EHLO, RTSP OPTIONS, etc.)
  5. Reads up to 512 bytes of response within the banner timeout
  6. Fingerprints the protocol and device type from the banner text
  7. Returns a ScanResult dataclass with all findings

Protocol Fingerprinting

Protocol Detection Method
HTTP / HTTPS Port 80/443/8080/8443 or HTTP/ in banner
SSH SSH- in banner or port 22
FTP ftp in banner or port 21
SMTP smtp in banner or port 25/587
POP3 +OK POP in banner or port 110
IMAP * OK in banner or port 143
RTSP rtsp in banner or port 554
Telnet telnet in banner or port 23

Connectivity Panel (Center)

Real-time connectivity status from two independent monitors: ICMP ping and TCP port probes.

Log format

Prefix Meaning
[ICMP] ● Ping reply received (target responding)
[ICMP] ⚠ Timeout or unreachable (ICMP may be blocked)
[TCP:80] ● Port open, connection accepted
[TCP:80] ✖ Timeout or error
[TCP:80] ↩ Connection refused (port closed, host reachable)

TCP probe lines include latency (ms) and a sequential probe number.

Why ICMP shows "timed out" but TCP shows "OPEN": Many servers block ICMP at the firewall while keeping TCP services running. If you see ICMP timeouts with TCP OPEN responses, the target is alive. TCP is the more reliable indicator.

Multi-Tab Sessions

TabbedContent widget with up to 4 simultaneous test tabs. Each tab is fully independent: its own Flooder, ping subprocess, TCP probe loop, stats timer, and log buffers.

Tab lifecycle

  1. Press Ctrl+N or use "New Test" from the palette
  2. SetupModal opens as an overlay
  3. Enter target, ports, bots. Submit.
  4. New TestTabPane created with a TestPanel inside
  5. Tab becomes active immediately
  6. Flood, ICMP, and TCP monitors start on mount

Tab labels

Show the target IP and primary port. Spinner animation (⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏) at 10 fps while running. Checkmark on completion.

  • Running: ⠹ 178.79.134.182:80
  • Complete: ✓ 178.79.134.182:80
  • Multiple ports: ⠹ 178.79.134.182 (80,443)

Closing tabs

Ctrl+W or "Close Tab" command. Stops the flooder, kills ping, stops stats timer, removes the pane.

Tab limit

Maximum 4. Warning notification if you try to open a 5th.

Background behavior

Inactive tabs keep running. TabbedContent hides panes via CSS but does not unmount them. Workers, subprocesses, and timers continue in all tabs simultaneously.

Internals

DOSPingCommandProvider extends Textual's Provider. search() uses self.matcher(query) for fuzzy matching. Each command yields a Hit with score, highlighted text, and async callback. Callbacks delegate to SessionScreen or TestPanel methods.

Event Log

New in 3.7.1: DOSping keeps a structured event log on disk — a verbose, grep-friendly audit trail of everything the app and its engines do, kept next to config.json.

Where the logs live

logs/
├── dosping-2026-09-14.log   ← today's file (active)
├── dosping-2026-09-13.log
└── dosping-2026-09-12.1.log ← size-rotated (.N suffix past 5 MB)

One file per local calendar day, stored in a logs/ folder beside dosping.py. When a file grows past the per-file cap it is rotated to .1/.2/… suffixes.

How a log line is built

Every event is one plain-text line with seven parts:

[ts] [level] [category] [session] event key=value …
FieldMeaning
ts local timestamp with milliseconds — 2026-09-14 21:04:11.482
level DEBUG, INFO, WARN or ERROR
category app · config · session · flood · scanner · settings · ui · error
session session/tab id (tab-1, scan-2) or - for app-global events
event snake_case event name, e.g. flood.workers_spawned
key=value … structured details: booleans as true/false, bytes as 512B, durations as 102.4s; strings containing spaces are quoted, newlines/tabs escaped and long values truncated (banners 120 chars) so one event is always exactly one line

Example lines

[2026-09-14 21:04:11.482] [INFO ] [app] [-] app.start version=3.7.1 python=3.12.7 os=Windows-11 terminal=120x38
[2026-09-14 21:04:11.517] [INFO ] [config] [-] config.load path=config.json changed_keys=0
[2026-09-14 21:04:29.130] [INFO ] [session] [tab-1] session.tab_opened kind=test target=203.0.113.7 ports=80,443 bots=200
[2026-09-14 21:04:29.140] [INFO ] [flood] [tab-1] flood.workers_spawned bots=200 concurrency=200 packet_size=512B reuse_payload=true ports=80,443
[2026-09-14 21:04:39.141] [INFO ] [flood] [tab-1] flood.stats interval=10.0s attempts=1842 ok=1203 fail=639 cps=184.2 errors=refused:610,timeout:29
[2026-09-14 21:06:11.902] [INFO ] [session] [tab-1] session.attack_finished duration=102.4s attempts=18874 ok=12293 fail=6581 success_rate=65.1%

What gets logged

  • App lifecycle — startup (version, OS, Python, terminal size), clean shutdown vs crash, unhandled exceptions on the main thread, worker threads and the asyncio loop.
  • Config — load (with migration notes), save (with the changed keys), section resets and factory resets.
  • Sessions — setup modal opened, every validation rejection (field + reason), validated parameters, tabs opened/closed, attack started / stopped (by whom) / finished (duration, attempts, ok/fail, success rate, bytes), scan started, monitor toggles.
  • Flood engine — worker pool spawned (bots, concurrency, packet size, payload reuse), aggregate stats every 10 seconds (never per-packet: a 1000-bot flood produces ~6 lines/minute, not thousands), sampled connection errors with reason classes (refused / timeout / cancel / dns / other), target health-check results.
  • Scanner — scan started (mode, target, port count, concurrency, timeouts, banner grab), progress milestones at 10 / 25 / 50 / 75 / 100 %, each open port with protocol/fingerprint/latency, banner contents (verbose+), finished summary.
  • Settings — every change (old → new), presets applied/created/deleted, theme changes, factory reset, editor discarded.

Verbosity levels

LevelIncluded
minimal app start/shutdown/crash, all errors, attack & scan start/finish
normal (default) everything above + config load/save, tab open/close, setup rejections, flood worker/stats events, scan milestones & open ports, settings changes
verbose everything above + full setup parameters, monitor toggles, health checks, banner contents, theme changes, exports
debug everything above + GeoIP results, latency samples, diagnostics

Errors are always recorded at every level (subject only to the master toggle).

Rotation & retention

  • Daily rotation — a new file per local date; size rotation past 5 MB per file (.1, .2, … suffixes).
  • Age cleanup — Delete Logs After (1 / 7 / 14 / 30 / 90 days / never) removes old files once at startup, based on the date in the filename (immune to clock-skewed mtimes). Today's active file is never deleted.
  • Size cleanup — Max Log Storage (10 / 25 / 50 / 100 / 250 MB / unlimited) caps the whole logs/ folder by deleting the oldest files first (again never today's file).
  • Manual wipe — ✕ Clear All Logs in the settings editor deletes everything except today's file and asks for confirmation first (respecting Confirm Dangerous).
  • Files locked by another process (Windows) are skipped and retried on the next launch — cleanup never crashes the app.

Performance & privacy

  • Writers never block the UI: events go through an in-memory queue drained by a background thread, and a gated event costs two integer compares.
  • Every record is flushed as it is written, so a crash loses at most the line being written.
  • Logs record the targets you test (IPs, ports, banners) — that is their purpose — but never your full config.json, and payloads are never written.
  • Log To Disk = off disables everything: no file is created or opened, and the in-app log panels are unaffected.

Auto-Updating

DOSping can check GitHub for a newer version and update itself in place with git pull. An update never restarts the app: restart DOSping yourself after it finishes.

Update channels

Channel Tracks What you get
stable (default) main branch Tagged releases.
dev dev branch Every commit, untagged, bleeding edge. May break.

Checking for updates

  • Manually — Settings → Advanced → Updates → Check Now, or the command palette (Ctrl+P) → Check for Updates.
  • Automatically — a non-blocking check runs on every launch. It only reports that an update exists; it never applies one. Startup checks fail silently. Turn this off with Auto-Check on Launch.

Applying an update

Update Now asks for confirmation, then runs:

  • git fetch origin <branch> and git checkout <branch>, so a channel switch takes effect.
  • git pull --ff-only origin <branch>, fast-forward only. It never creates a merge commit.
  • pip install -e ., which picks up new dependencies.

It refuses to run while tracked files have local changes, so hand edits are never overwritten. Untracked files (your own notes, for example) do not block it.

Update settings

Key Type Default Meaning
advanced.update.channel string "stable" stable or dev.
advanced.update.auto_check bool true Check GitHub on every launch.
advanced.update.last_checked string "" ISO timestamp of the last check.
advanced.update.last_check_status string "" up_to_date, update_available, or error.

To install from the dev channel, run bash setup.sh --channel=dev (or setup.bat --channel=dev). The default is stable.

Flood Engine

Flooder class in flooder.py. No UI dependencies. Communicates through callbacks.

How it works

  1. run() creates asyncio.Semaphore(50)
  2. Schedules _attack() for each bot (0 to bots-1)
  3. Ports assigned round-robin: ports[i % len(ports)]
  4. asyncio.gather() runs all, gated by the semaphore

Single connection (_attack)

  1. Check stop flag
  2. Acquire semaphore (blocks at 50 concurrent)
  3. asyncio.open_connection(target, port) with 3s timeout
  4. Write 1024 random bytes
  5. Drain write buffer
  6. Close writer
  7. Increment successful + bytes_sent
  8. On exception: increment failed
  9. Record monotonic timestamp for rate calculation
  10. Fire on_progress(current, total)
  11. Every 25 connections: fire on_log()

Rate calculation

connections_per_sec(window=5.0) counts timestamps in the last 5 seconds, divides by window. Old timestamps pruned each call. Smooth rolling average.

Stopping

stop() sets _stopped. Each coroutine checks before semaphore acquisition and before connecting. Running connections finish normally. Flood drains in seconds.

ICMP Monitor

Async worker in TestPanel. Spawns system ping as a subprocess, streams stdout.

Platform commands

OS Command Behavior
Windows ping -t <target> Continuous
Linux/macOS ping <target> Continuous

Line classification

  • "reply from" or "bytes from" = success
  • "timed out" or "unreachable" = timeout (note: ICMP may be blocked)
  • "pinging" or "ping" = informational header
  • Everything else = muted

Toggle

Off: ping subprocess killed, loop sleeps. On: new subprocess starts automatically.

TCP Probe Monitor

Async worker alongside ICMP. Probes each target port every 2 seconds. 3-second timeout.

Results

Result Symbol Meaning
OPEN ● Connection accepted. Includes latency (ms).
TIMEOUT ✖ 3s elapsed. Port may be filtered.
REFUSED ↩ RST received. Host reachable, port closed.
Error ✖ Other OS error.

vs. the flood

TCP probe is read-only: opens, closes, measures latency. No payload. The flood sends 1 KB per connection. They run on separate workers.

Toggle

Off: loop sleeps. No subprocess involved, so toggle is instant.

Troubleshooting

"ICMP timed out" but "TCP OPEN"

Normal. Many hosts block ICMP at the firewall. TCP probe is the accurate indicator.

All connections fail (100% miss rate)

  • Check if the target is reachable (ping from a normal terminal)
  • Verify the port is open (telnet or nmap)
  • ISP or firewall may be blocking outbound connections
  • Target rate limiting or IPS dropping connections

CSS error in stylesheet

DOSping uses f-string hex injection into CSS (not Theme.variables). Check color format is #rrggbb, no alpha, no rgb().

"Max 4 concurrent tests"

Close an existing tab with Ctrl+W first.

setup.sh: permission denied

Run with bash setup.sh explicitly, or chmod +x setup.sh && ./setup.sh.

Python not found

Install Python 3.12+ from python.org. Windows: check "Add to PATH". Linux: apt install python3 or pacman -S python.

Still stuck? Open an issue at github.com/debug-cli/dosping/issues with OS, Python version, and full error output.
